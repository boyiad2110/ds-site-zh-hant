# Draw Steel 中文工具設計規範

> 狀態：正式設計語言
>
> 視覺方向：英雄譜印（Living Heraldry）
>
> 建立日期：2026-08-02
>
> 適用對象：產品設計、前端實作、內容呈現與 Review

本文件把已批准的 UI／UX 決策整理成可執行、可驗收的設計規範。它是活文件；正式裁決或經驗證的實作基準改變時，應同步更新，但不得以實作便利為由改動產品範圍、正式術語、資訊層級或 Living Heraldry 核心方向。

---

## 1. 文件目的、適用範圍與權威層級

### 1.1 文件用途

`DESIGN.md` 是：

- 後續 Agent 與開發者的前端設計規範。
- 設計、實作與 Review 的共同驗收依據。
- 設計原則、語意角色、頁面與元件責任、互動狀態及反模式的紀錄。
- 可隨正式裁決與實作驗證更新的活文件。

`DESIGN.md` 不是：

- UI／UX 研究報告或 mockup 的逐頁說明。
- 單一懲戒者頁面的 CSS 規格。
- 完整產品 roadmap、資料 schema 或路由設計文件。
- 對長期方向或未批准資料域的開發授權。

### 1.2 權威分工

各正式來源依議題分工，不使用單一線性順序互相覆寫：

| 來源 | 權威責任 |
|---|---|
| 擁有者的最新明確裁決 | 所有議題的最高權威 |
| [`docs/scope.md`](./scope.md) | 決定目前批准收錄與開發的內容範圍 |
| [`data/decisions.json`](../data/decisions.json) 與 [`data/glossary.json`](../data/glossary.json) | 決定正式術語及翻譯裁決 |
| 本文件 | 決定 UI／UX、視覺語言與呈現規則 |
| 現有實作與概念 mockup | 只作驗證與參考，不反推正式決策 |
| 通用設計指引與 Skill 建議 | 補充檢核，不得覆寫專案正式決策 |

`scope.md` 中的歷史術語不得推翻已批准 glossary；同理，術語文件不擴張 milestone scope，本文件也不裁定資料模型或 URL。若正式術語、產品範圍、頂層 IA、URL、資料模型或 Living Heraldry 核心方向出現實質矛盾，不得由實作者自行選擇，必須請擁有者裁決。非阻塞的待決事項應明確標記，不得以暫時實作反推正式決策。

## 2. 產品結構與功能邊界

### 2.1 長期頂層結構

長期頂層產品區域固定為：

**規則｜資料｜英雄**

| 區域 | 正式責任 | 不代表 |
|---|---|---|
| 規則 | 呈現正式 scope 已批准的基本規則、檢定、戰鬥、談判、休整及其他規則內容 | 官方規則書所有章節皆已批准收錄 |
| 資料 | 呈現正式 scope 已批准的族裔、文化、職業、範型、套裝、專長、糾葛、招式等結構化遊戲資料 | 所列資料域都已進入目前 milestone |
| 英雄 | 建立英雄與管理已建立的英雄 | 遊戲中操作介面或 VTT |

正式頂層名稱一律使用「資料」，不使用「資料庫」。全域搜尋是跨頁核心能力，但不是第四個產品區域。

### 2.2 英雄功能邊界

「英雄」只包含：

- 建立英雄。
- 英雄管理。
- 保存、查看、分享及匯出英雄資料。
- 查看英雄已選內容與完整規則。

明確排除：

- Hero runner。
- 網站內戰鬥操作。
- 回合管理或狀況操作。
- 即時英雄資源追蹤。
- 牌桌操作 dashboard。
- 取代 VTT。

「遊戲時查閱網站」不等於「使用網站操作遊戲」。規則、資料與已建立英雄的內容可以在跑團中查閱，但網站不承擔即時戰鬥狀態。

### 2.3 Director 邊界

- 現階段以玩家為主要使用者。
- 不建立 Director 頂層入口或空 dashboard。
- Director 規則是否收錄及何時收錄，由後續 scope 決定。
- 只有 Director 工具正式批准並開始開發後，才建立獨立產品區。

### 2.4 三個範圍層級

| 層級 | 已知範圍 | 規範解讀 |
|---|---|---|
| 長期產品方向 | 規則／資料／英雄，以及已批准的英雄建立與管理方向 | 決定可擴充的 IA 與設計語言，不等於開發授權 |
| 目前正式 scope | M0：懲戒者一級資料切片；M1：神導士一級資料切片 | 實際設計與開發不得自行超出 [`docs/scope.md`](./scope.md) |
| 現有實作 | 69 筆累積 catalog、搜尋與規則庫、範型索引與範型總覽、通用條目頁與範型脈絡條目頁 | 用來驗證設計；不是完整產品規格 |

未來資料規模不得由目前 69 筆 catalog 推算；目前 manifest 也不得被視為所有資料域的長期模型。

## 3. 正式術語

下列中英文對應固定使用：

| 英文 | 正式繁體中文 |
|---|---|
| Class | 範型 |
| Career | 職業 |
| Subclass | 子範型 |
| Ancestry | 族裔 |
| Culture | 文化 |
| Kit | 套裝 |
| Perk | 專長 |
| Complication | 糾葛 |

規則：

- 不得將 Class 翻譯或泛稱為「職業」。
- 不得以「職業」作為「範型」的輔助說法。
- 「懲戒者」與「神導士」是範型；「懲戒者教團」是子範型選擇脈絡。
- 導覽、篩選、切換器、麵包屑、頁面標題、譜印標示與替代文字都必須遵守相同術語。
- 英文正典名稱可作輔助資訊，但中文正式名稱是主要標籤。

## 4. 核心設計與 UX 原則

1. **先回答任務，再展示個性。** 搜尋、規則結算與資料定位永遠優先於裝飾。
2. **身份可辨，正文可信。** 範型身份區可鮮明；規則正文必須穩定、清楚、適合長時間閱讀。
3. **總覽與詳情各司其職。** 範型總覽回答「這個範型有哪些內容？」；條目頁回答「這條規則如何使用與結算？」
4. **同一資料，多種脈絡。** 搜尋、資料瀏覽、範型總覽與英雄已選內容可以引用同一條規則，不複製出互相漂移的正文。
5. **掃讀順序符合遊戲判定。** 招式資訊依費用、動作、射程、目標、檢定、結果與效果呈現。
6. **手機重排，不縮印。** 小螢幕依任務優先順序重組，不把桌機多欄硬縮成一欄。
7. **可見狀態必須可理解。** 狀態不能只靠顏色、hover、圖示字型或動作暗示。
8. **效能依量測決定。** 長列表是否分頁、延遲載入或 virtualization 由真實效能與無障礙測試決定，不設固定條目數門檻。

## 5. Living Heraldry 視覺語言

### 5.1 核心構成

- 淺色規則內容表面承載閱讀與結算。
- 深色範型身份區承載範型名稱、英文名、短介與機制導向譜印。
- 範型身份色建立辨識；英雄資源色只標示相應資源。
- 譜印描述機制或玩法特徵，不是通用奇幻徽章。
- 裝飾克制，靠比例、字體、色塊與對齊建立個性。

### 5.2 視覺邊界

不得把產品做成：

- 一般 Wiki 或文章資料站。
- SaaS dashboard。
- 全站深色戰術介面。
- 技術手冊式索引。
- 紙本規則書逐頁仿製。
- 堆疊徽章、金框、羊皮紙紋理或無功能奇幻紋樣的介面。

現有 mockup 是概念參考，不是逐像素定稿。版面可在不破壞上述核心的前提下，因內容、響應式與無障礙驗證而調整。

## 6. 語意色彩及其使用邊界

### 6.1 第一版語意基準

| 語意角色 | 基準值 | 使用方式 |
|---|---:|---|
| 全站畫布 | `#E8ECE8` | 頁面背景與區域分隔；不作正文卡片底色 |
| 規則內容表面 | `#F8F8F3` | 正文、列表、規則卡與主要閱讀表面 |
| 主文字 | `#202B35` | 標題、正文與高重要資訊 |
| 次要文字 | `#5B686B` | 英文名、來源、輔助說明；不得用於需要更高對比的細字 |
| 互動／連結 | `#1E527A` | 文字連結、可操作標記與主要互動 |
| 鍵盤焦點 | `#A16207` | `:focus-visible` 外框；不可兼作 selected 的唯一訊號 |
| 懲戒者範型色 | `#243F66` | 懲戒者身份區、局部導覽標記與譜印 |
| 神導士範型色 | `#5F4A73`（暫定） | 神導士身份區、局部導覽標記與譜印 |
| 怒火 | `#8F3F3A` | 怒火名稱、費用與摘要帶資源標記 |
| 虔誠 | `#2E6D67` | 虔誠名稱、費用與摘要帶資源標記 |
| warning 前景／表面 | `#8A4B08`／`#FFF4DB` | 非阻塞風險與需注意事項，必須附文字 |
| error 前景／表面 | `#B42318`／`#FDEBE9` | 錯誤與失敗，必須說明原因及恢復方式 |
| success 前景／表面 | `#276749`／`#E8F5EC` | 已完成或保存成功，不得長期占據主要層級 |

### 6.2 使用規則

- 元件使用語意 token，不在個別頁面重新發明顏色。
- 範型色屬於身份，不代表連結、成功或 selected。
- 英雄資源色只用於該資源的名稱、費用、數值或摘要帶，不鋪滿正文。
- selected 必須同時有形狀、底色、邊線或文字狀態；不能只改顏色。
- warning、error、success 必須搭配可讀文字及適當語意，不以色彩單獨傳意。
- 深色身份區上的文字與互動控制必須個別通過 WCAG AA，不假設白字必然合格。
- 色碼是第一版基準，可依對比與實機驗證微調；不得改變色彩語意、資訊層級或產品邊界。

## 7. 字體角色與資訊層級

| 角色 | 字體 | 第一版基準 | 規則 |
|---|---|---|---|
| 品牌與範型名稱 | Noto Serif TC | 32–44px／600–700 | 只用於高身份層級，不進入密集控制列 |
| 頁面與章節標題 | Noto Serif TC | 24–32px／600–700 | 以層級、間距與字重建立結構 |
| 子標題與卡片標題 | Noto Serif TC 或 Noto Sans TC | 18–22px／600 | 規則名稱可保留襯線；操作型標題用無襯線 |
| 規則正文 | Noto Sans TC | 16–17px／400，行高 1.6–1.75 | 手機正文不得小於 16px |
| 英文名稱 | Noto Sans TC 拉丁字形 | 13–16px／400–500 | 作輔助辨識，不搶過中文名稱 |
| 數值、費用與規則標籤 | Noto Sans TC | 13–16px／500–700 | 使用 tabular numerals；數值與單位不可拆散 |

規則正文不使用全大寫、極細字重或大段斜體。正式繁體中文內容不為了追求密度而壓到 12px 以下。字級與行高是第一版基準，可經 200% zoom、實機與字體載入驗證微調，但不得顛倒資訊層級。

## 8. 間距、密度、行長、框線與表面

### 8.1 第一版基準

- 以 4px 為最小節奏，常用間距為 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px`。
- 行動控制間至少保留 8px，避免誤觸。
- 桌機規則正文理想行長約 34–42 個全形中文字；手機依可用寬度自然換行，不追求桌機行長。
- 長文閱讀欄第一版以約 `720–780px` 為上限；總覽可使用較寬容器，但正文不橫跨整個 1440px 畫面。
- 區塊之間用間距、對齊與少量分隔線分組，避免每段都變成獨立卡片。
- 規則表面以平面或極低陰影為主；陰影只表達浮層或層級，不作裝飾。
- 圓角保持克制，第一版以 `2–6px` 為主；不可把所有容器做成相同大圓角 SaaS 卡片。
- 框線應服務分組與掃讀，不使用裝飾金框或多重邊線。

數值可因內容與可用空間微調，但應維持相同節奏、閱讀行長與密度層級。

## 9. 響應式與手機轉換原則

### 9.1 第一版 breakpoint 基準

- compact：小於 `600px`。
- medium：`600–899px`。
- wide：`900px` 以上。

breakpoint 是第一版驗證起點，不是裝置名稱或固定產品契約；應以內容開始擁擠或失去層級的時點微調。

### 9.2 轉換規則

- 手機維持單一主要捲動區，避免巢狀捲動與必要的橫向捲動。
- 全域頁首壓縮後仍須保留目前位置、搜尋入口與返回路徑。
- 範型身份、英雄資源摘要、章節導覽、列表與條目內容依任務順序垂直排列。
- 桌機側欄或章節 rail 在手機改為可見的章節入口、展開區或頁內跳轉；不可只靠橫向 swipe。
- 表格若無法安全縮排，改成有標籤的逐列資料，不縮小字體硬塞。
- 320px 寬度必須可讀、可操作、無內容裁切；200% zoom 時仍維持單一可理解流程。
- 固定或 sticky 控制不得遮住內容、焦點目標、瀏覽器安全區或系統手勢區。
- 手機的範型總覽維持「總覽優先」；完整招式規則進入條目頁，不在總覽首屏塞入完整卡。

## 10. 全域導覽與搜尋

### 10.1 全域導覽

- 長期主導覽固定為「規則／資料／英雄」。
- 搜尋為全域能力，與主導覽同層可達，但不列為第四產品區。
- 當前位置需以文字、字重與視覺指示共同表達；不得只靠顏色。
- 深頁必須提供可預測的返回路徑，並保留原有搜尋條件、列表位置及必要的捲動狀態。
- 三層以上的內容脈絡應顯示可理解的階層路徑；名稱使用正式術語。

### 10.2 搜尋

- 桌機與手機深頁都能快速進入搜尋，不要求先回首頁。
- 搜尋欄使用可見標籤或可理解的 accessible name；placeholder 不代替標籤。
- 結果至少顯示中文名稱、英文名稱、資料類型與所屬脈絡，讓「審判」等近似詞可辨識。
- 搜尋結果與空結果要說明查詢內容；錯誤要提供重試或返回方式。
- 鍵盤操作需支援輸入、結果移動、開啟與返回，順序與視覺順序一致。
- 動態結果數與搜尋錯誤使用適當的 live region 宣告，但不在每次按鍵造成干擾式播報。

現有「規則庫」與品牌中的「資料庫」是現況標籤，不構成長期 IA 的正式命名。修改它們需要另行進入批准的實作範圍。

## 11. 規則、資料、英雄三區的頁面責任

| 頁面／區域 | 主要問題 | 必須優先呈現 | 邊界 |
|---|---|---|---|
| 首頁 | 我可以從哪裡開始？ | 全域搜尋、規則／資料／英雄入口、目前 scope 已可用內容 | 不以 69 筆 catalog 或兩個範型定義完整產品 |
| 規則 | 這項規則如何運作？ | 規則主題、章節脈絡、完整正文與相關引用 | 只呈現正式 scope 已批准內容 |
| 搜尋結果 | 哪個結果符合我的問題？ | 查詢、結果類型、名稱、英文名與脈絡 | 不把所有實體壓成無差異文章列表 |
| 資料索引 | 有哪些結構化遊戲資料？ | 資料域入口、名稱、辨識資訊與可用範圍 | 資料域出現不等於其 schema 已定案或已批准實作 |
| 英雄 | 我要建立或管理哪位英雄？ | 建立英雄、英雄清單／詳情、保存／分享／匯出及已選內容 | 不提供 Hero runner 或即時牌桌操作 |

同一規則從不同入口開啟時，頁面可保留來源脈絡與返回路徑；canonical URL 與跨資料域模型尚未定案。

## 12. 範型索引、範型總覽及條目頁模式

### 12.1 範型索引

責任是回答「有哪些已收錄範型？」並讓使用者辨識與進入範型。每個範型項目至少包含中文名稱、英文名稱、簡短定位與身份色／譜印之一；不可只用顏色區分。

### 12.2 範型總覽

責任是回答「這個範型有哪些內容？」應依序呈現：

1. 範型身份：例如「懲戒者／Censor」、簡介與機制導向譜印。
2. 英雄資源摘要：例如怒火的用途與取得方式快速摘要。
3. 核心特性：例如懲戒者教團、審判。
4. 章節與招式分類：例如招牌招式、3 點怒火招式、5 點怒火招式。
5. 個別招式摘要與進入完整條目的明確入口。

總覽不重複完整規則卡，也不把每個條目內容全部展開造成長頁失焦。

### 12.3 條目詳細頁

責任是回答「這條規則或招式如何使用與結算？」應呈現：

- 完整且唯一可信的規則內容。
- 所屬資料域、範型與章節脈絡。
- 返回範型總覽或來源列表的路徑。
- 可切換的相關條目入口；不得只靠 swipe。
- 來源、版本及英文正典資訊。

條目頁可由通用路徑或範型脈絡路徑進入；兩者的正式關係與 canonical URL 留待後續處理。

## 13. 招式摘要、列表與完整規則卡的內容界線

### 13.1 招式摘要

用於範型總覽與搜尋結果，應包含：

- 中文名稱與英文名稱。
- 招式分類與費用，例如「5 點怒火」。
- 動作類型。
- 一句效果摘要或可辨識的 flavor；兩者需明確區分。
- 進入完整條目的可見入口。

摘要不得截取到改變規則意義，也不得假裝自己是完整規則。

### 13.2 招式列表

- 依正式章節或招式分類分組，而非依卡片視覺任意排列。
- 各列維持相同欄位順序，便於比較費用、動作與用途。
- 桌機可使用多欄；手機改為有標籤的垂直資料列。
- 空分類清楚說明目前 scope 無內容，不用假資料填滿。

### 13.3 完整規則卡

固定掃讀順序：

1. 名稱與費用。
2. 英文名、分類與等級。
3. 關鍵詞與動作。
4. 觸發。
5. 射程與目標。
6. 檢定屬性。
7. 三階結果。
8. 效果。
9. 額外花費與後續結算。
10. 來源與相關內容。

條目沒有某個欄位時直接省略，不顯示空框、空標籤或占位符，也不為維持版面對齊而製造假資料。

真實例子「當場拘捕／Arrest」應清楚顯示「5 點怒火 → 主要動作 → 近戰 1 → 1 個生物 → 力量檢定 → 三階結果 → Effect」。三階結果依序為「≤11：6 + 力量神聖傷害；擒制」、「12–16：9 + 力量神聖傷害；擒制」、「17+：13 + 力量神聖傷害；擒制」，其後才呈現被擒制目標發動打擊時可花費 3 點怒火的效果。

## 14. 範型譜印與身份區使用規則

- 每個範型最多有一個主要譜印系統；同頁不增加多個競爭徽章。
- 譜印必須源自機制或玩法身份，例如懲戒者的審判、拘束與怒火關係，而非泛用劍盾圖案。
- 譜印可出現在範型索引、範型總覽身份區及小型來源標記；不可作正文浮水印干擾閱讀。
- 深色身份區只用於建立範型脈絡，不擴張成全站深色介面。
- 身份色不能取代範型名稱、文字標籤或階層路徑。
- 職業、文化、族裔等其他資料域未經設計決策，不自動套用「範型譜印」或範型身份色規則。
- 譜印必須有適當替代文字或標記為純裝飾；不可使用符號字型承載意義。

## 15. 英雄資源摘要帶

英雄資源摘要帶是規則導覽，不是即時資源追蹤器。固定資訊結構為：

1. 資源名稱與英文名稱，例如「怒火／Wrath」。
2. 所屬範型。
3. 一句用途：資源驅動哪些招式或效果。
4. 戰鬥開始時的取得基準。
5. 戰鬥中的主要取得觸發。
6. 結束或戰鬥外的關鍵限制。
7. 進入完整規則條目的入口。

懲戒者的快速摘要可呈現：「緊張情境開始時獲得等於勝利值的怒火；每輪回合開始獲得 2 點；首次與被審判生物互相造成傷害時各有取得條件；遭遇結束時失去剩餘怒火。」摘要必須連回完整「怒火」條目，不以摘要取代戰鬥外規則。

摘要帶不得提供加減按鈕、目前值、回合自動結算或其他 Hero runner 行為。

## 16. 互動與系統狀態

### 16.1 狀態矩陣

| 狀態 | 視覺要求 | 行為要求 | 無障礙要求 |
|---|---|---|---|
| default | 清楚顯示可互動性與標籤 | 不依賴使用者猜測 | 使用正確原生語意與 accessible name |
| hover | 輕微變更底色、邊線或文字裝飾，不位移版面 | 只作滑鼠輔助 | 重要資訊不得只在 hover 出現 |
| focus-visible | 使用高辨識焦點色、2–3px 外框與適當 offset | 焦點不被 sticky 元件遮住 | 只在適當鍵盤互動顯示，順序符合閱讀順序 |
| active／pressed | 即時且不改變版面尺寸的按壓回饋 | 不重複送出動作 | 保留控制名稱與狀態 |
| selected | 以底色／邊線／字重及文字或語意屬性共同表示 | 與 focus、active 分離 | 使用 `aria-current`、`aria-selected` 等符合元件的語意 |
| disabled | 降低強調但仍可辨識，不只降低透明度 | 不可操作；必要時說明原因 | 使用原生 disabled 或等效語意，不進入無意義焦點順序 |
| read-only | 外觀與 disabled 可區分，內容仍可選取與閱讀 | 不允許編輯，但可複製與導覽 | 明確宣告唯讀狀態 |
| loading | 保留預期空間，使用穩定骨架或進度文字 | 避免重複操作與版面跳動 | 容器標示 busy；完成後合理管理焦點與宣告 |
| empty | 說明為何無內容及可行下一步 | 不用假資料或無關 CTA 填空 | 訊息進入正常閱讀順序 |
| success | 簡潔確認已完成事項 | 不遮斷下一步，不自動奪取焦點 | 使用 polite live region；不能只顯示綠色 |
| warning | 說明風險與可繼續方式 | 不把一般提示偽裝成錯誤 | 文字與語意同步，不只顯示黃色 |
| error | 就近顯示原因、受影響範圍與恢復方式 | 表單聚焦第一個錯誤；請求可重試 | 多錯誤有摘要與欄位連結，動態錯誤可被讀屏宣告 |

### 16.2 動效

- 動效只表達狀態、層級或因果，第一版微互動以約 `150–250ms` 為基準。
- 不以大幅位移、視差、連續閃爍或裝飾性進場建立「遊戲感」。
- 動效不得造成 layout shift 或阻擋輸入。
- `prefers-reduced-motion: reduce` 下移除非必要移動，保留立即可理解的狀態變化。

## 17. 無障礙要求

所有已實作頁面與狀態至少符合：

- WCAG 2.2 AA；一般文字對比至少 4.5:1，大型文字與必要 UI 圖形依相應門檻驗證。
- 所有觸控目標至少 44×44px，彼此保留足夠間距。
- 完整鍵盤操作；Tab 順序與視覺順序一致，無鍵盤陷阱。
- 清楚且不被裁切的 `:focus-visible`，不可移除焦點外框而無等效替代。
- 支援 `prefers-reduced-motion`。
- 支援 200% zoom，不停用瀏覽器縮放，不產生必要的雙向捲動。
- 使用正確的 `header`、`nav`、`main`、`aside`、`footer` 等 landmarks；每頁一個可辨識 `h1`，heading 不跳級。
- 提供跳至主要內容連結。
- 不依賴 hover、顏色、符號字型或橫向 swipe 傳遞重要資訊。
- 圖示按鈕有可理解名稱；結構圖示使用一致 SVG 語言，不用 emoji 或字型圖示承載功能。
- 搜尋結果數、載入完成與表單錯誤有適度讀屏宣告，不造成逐鍵噪音。
- 路由切換後，焦點移至頁面主標題或主要區域；返回時盡可能恢復觸發控制、搜尋條件與捲動位置。
- 字體載入失敗時仍有可讀 fallback；正文不因字體交換發生不可接受的跳動或裁切。

現有自動化無障礙測試是基線，不取代鍵盤、讀屏、zoom、reduced motion 與實機觸控人工驗收。

## 18. 長期擴充原則

- 「規則／資料／英雄」提供長期穩定入口；新增內容先歸入已批准區域，不輕易增加頂層導覽。
- 族裔、文化、職業、範型、套裝、專長、糾葛、招式共用名稱、英文名、來源、版本、狀態與引用等展示角色；正式 schema 仍由後續資料模型階段決定。
- 範型身份色與譜印採可擴充 token 與資料驅動映射，不在元件內寫死懲戒者或神導士判斷。
- 其他資料域可共用規則表面、字體、搜尋、來源與狀態語言；不得未經決策複製範型的深色身份區與譜印。
- 英雄建立與英雄管理應引用同一正式規則與資料條目；保存、分享、匯出格式留待正式資料模型決定。
- 內容增加時維持可搜尋、可深連結與可返回的脈絡；canonical URL 與跨資料域引用模型未定案前不由 UI 規範推導。
- 是否採用分頁、漸進載入或 virtualization，依資料量、輸入延遲、捲動表現、讀屏與焦點恢復的實測決定。
- 現有範型 manifest 可服務目前切片，但其長期拆分方式仍待決，不得作為其他資料域模板的既定答案。
- Director 工具不在現階段核心範圍；只有正式批准後才設計獨立產品區。

## 20. 決策狀態

### 20.1 已確定

- 長期頂層 IA：規則／資料／英雄。
- 英雄只包含建立與管理，以及保存、查看、分享、匯出與已選內容查閱。
- 排除 Hero runner、網站內遊戲操作與 VTT 替代方向。
- Director 工具僅在未來正式批准後建立獨立產品區。
- 正式術語表與「範型／職業」區分。
- Living Heraldry 核心方向。
- 淺色規則表面、深色範型身份區、搜尋核心地位。
- 範型總覽與條目詳細頁分工。
- Noto Serif TC／Noto Sans TC 角色分工。
- WCAG AA、44×44px、鍵盤、focus-visible、reduced motion 與 200% zoom 基線。

### 20.2 可經實作驗證微調

- 色碼的精確明度與對比配對。
- 字級、行高、字重與閱讀欄寬。
- breakpoint、容器寬度與 gutter。
- 間距、框線、圓角、陰影與動效時間。
- 長列表的分頁、漸進載入或 virtualization 策略。

微調不得改變色彩語意、資訊層級、正式術語、產品邊界或 Living Heraldry 核心。

### 20.3 後續待決，不得在本文件定案

- canonical URL。
- 一般條目與範型脈絡路徑的正式關係。
- 跨資料域引用模型。
- 職業、文化、套裝等資料域的正式 schema。
- 英雄保存、分享與匯出的正式資料格式。
- Director 規則內容的收錄 scope。
- 現有 manifest 的長期拆分方式。

這些事項應留到後續資料模型、IA 或 scope 階段處理；目前維持既有連結相容性，不由設計元件自行創造答案。
