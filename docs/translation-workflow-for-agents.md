# 翻譯流程總覽 —— 給接手的 AI Agent

> 建立於 2026-07-30。
> **這份文件的用途是「教會一個沒有本專案記憶的 AI Agent 怎麼在這裡工作」。**
>
> 它**不是**新的權威。所有規則的權威仍在原處：
> 範圍 → `docs/scope.md`；規則與 schema → `docs/translation-guide.md`；
> 現況與基線數字 → `NEXT-SESSION.md`。

## 0. 三十秒版本

| | |
|---|---|
| **在做什麼** | 把 Draw Steel（MCDM 桌上 RPG）的官方英文規則，做成一個正體中文規則庫網站 |
| **工作的性質** | **不是從零重譯，是「對齊」** —— 專案已有完整舊譯與舊術語表，工作是核對新版正典、找出差異、補上缺漏 |
| **AI 的角色** | 抽取、比對、產草稿、寫報告。**不是裁決者** |
| **誰裁決** | 專案擁有者，唯一權威。擁有者無程式背景，說明要白話 |
| **最大的敵人** | 不是翻錯，是**流暢但錯誤**、**靜默的順序錯亂**、**假裝驗證過** |

## 1. 核心心態：這是稽核工作，不是創作工作

一般翻譯任務的品質標準是「讀起來好不好」。**這裡不是。**

這裡的產出會被人拿到牌桌上照著用。一個漏掉的「不」、一個寫錯的門檻數字、
一個沒譯出的限定語（`on the target`、`willing`、`adjacent`），
讀起來完全正常，直到有人依它做出錯誤的規則裁決。

因此整套流程的設計邏輯是：

> **AI 生成中文的過程內部沒有可稽核的步驟鏈。
> 所以紀律必須建立在 AI 之外 —— 用分類、標記、報告格式、腳本驗證把它包起來。**

這句話是理解本專案所有奇怪規定的鑰匙。為什麼要三個維度的標記？
為什麼相符的欄位不准逐欄展開、卻要求附上逐條目欄位帳？
為什麼數字一定要「從清單長出來」？——都是同一個理由：**讓錯誤沒地方躲**。

## 2. 角色與權限

| 角色 | 能做 | 不能做 |
|---|---|---|
| **專案擁有者** | 所有裁決：術語、範圍、譯法、資料模型 | — |
| **AI Agent** | 抽取正典、逐欄比對、產出 `draft` 中文、寫報告、寫腳本、跑驗證 | ❌ 自行批准術語<br>❌ 自行造詞<br>❌ 自行改寫舊譯<br>❌ 自行擴大範圍<br>❌ 把 `draft` 升成 `approved`／`reviewed` |
| **外部 AI Review** | 擁有者會拿高強度外部 review 檢查交付物 | — |

**推論：交付時要附 manifest，誠實列出限制與未覆蓋範圍。**
不要宣稱超出實際驗證的保證 —— 外部 review 會抓到，而且抓到過很多次（見 §8）。

## 3. 權威順序

衝突時一律依此裁決，**沒有例外**：

| 順位 | 來源 | 決定什麼 |
|---|---|---|
| 1 | **英文正典 —— Heroes 原版規則書內文**（`sources/official/Draw_Steel_Heroes_v1.01/*.pdf`） | 規則含義 |
| 2 | **`approved` glossary / vocabulary** | 固定術語 |
| 3 | **`docs/translation-guide.md`** | 語氣、句法、格式 |
| 4 | **舊譯**（`sources/notion-export/`） | 既有風格的**證據**與遷移來源 |
| 5 | **AI** | 草稿與建議 |

### 3.1 三個容易踩的坑

**(a) 舊譯不是權威。** 它可能與舊術語表衝突（`Triggered Action`：舊譯 135 檔一致用「觸發式動作」，
舊術語表寫「反應動作」），也可能來自舊版規則。它是規則的**來源**，不是標準。

**(b) 只有 Heroes 規則正文算正典。** 下列都只是參考，且**不得進入 `data/canon/`**：
`DrawSteelRulesReferenceV1.pdf`（本階段完全不用，且因它產生過假指控）、
Heroes 自己的詞彙表頁（索引式摘要，連觸發條件都與正文不同）、
Foundry VTT／Forge Steel／Steel Compendium（授權因素排除）。

**(c) `approved` 是裁決的結果，不是裁決的理由。**
不可以寫「因為術語表是權威所以採用表上的值」——那是循環論證。
要記錄實際發生的事：擁有者看了哪些證據、批准了什麼。

## 4. 全流程

```
① 確認範圍  ──→ ② 抽取英文正典 ──→ ③ 產術語依賴清單
                        │
                        ↓
                 ④ 逐句對齊舊譯 ──→ ⑤ 寫對齊報告 ──→ ⑥ 擁有者裁決
                                                          │
                                                          ↓
                                   ⑧ 網站呈現 ←── ⑦ 產出中文 draft
```

### ① 確認範圍

**動手前先確認要做的東西在不在 `docs/scope.md` 裡。**

⚠️ 範圍的權威是那份文件與擁有者，**不是來源 PDF 的頁面內容**。
曾發生一次誤判：把「某某頁涵蓋範圍」理解成去讀那頁 PDF 上有什麼，
於是多做了三張不屬於範圍的卡，事後全數刪除。

範圍不明時：**先問擁有者，不要自行擴大解釋。**

### ② 抽取英文正典 → `data/canon/`

採**混合抽取法：文字為主，圖像驗結構**。

1. 每個 PDF 章節先算繪 **1–2 頁 150dpi**，確認版面結構（哪些條目在哪個標題下、有無側欄穿插）
2. 結構確認後，用 **`pdftotext -layout`** 逐個條目取內容
3. **用舊 CSV 交叉驗證**等級、費用、分類 —— 不一致才算繪那一頁

第 3 點是關鍵：**兩個獨立來源互相檢核**，比單靠算繪可靠（算繪只有 AI 一雙眼睛）。

**兩條硬性規定：**

- **`pdftotext` 一定要加 `-layout`。** 不加會**靜默**毀掉左欄的卡片：
  階層符號 `á é í` 被抽離、與數值失聯，數值漂到 40 行外，還混進隔壁卡片的欄位。
- **算繪預設 150dpi。看得清楚就不要再畫 300dpi。**
  150dpi 全頁約 2,800 tokens、300dpi 約 11,000。已經讀得出來還去放大＝白花一次判讀成本。
  流程：先算繪 150dpi →**實際讀過**→ 讀得出爭議字句就寫下該圖路徑，結束。

具體指令見 `NEXT-SESSION.md` 的「正典抽取方法」一節（含 poppler 絕對路徑）。

**產出兩個檔：**
- `data/canon/<type>/<id>.json` —— 結構化正典
- `data/canon/_normalized/<id>.txt` —— 供計算 `normalizedHash` 的逐字快照

### ③ 產出精確術語依賴清單 → `releases/m0.json`

**glossary 範圍不得用估算。** 清單來源必須涵蓋該里程碑的**全部發布文字**。

掃描有三個通道（`scripts/lib/m0-scan.mjs`，`report-m0-terms` 與 `build-m0-release` 共用同一份，
不會各說各話）：

| 通道 | 來源 | 可信度 |
|---|---|---|
| A · 受控值 | 全部影響中文呈現的結構欄位 | 確定性，免複核 |
| B · 散文文字比對 | 敘述、說明、段落 | **必然有假命中**，每筆留上下文 |
| C · 疑似缺詞 | 把命中遮掉後剩下的規則用語 | 需人工判斷 |

三個「不算數」的出口（`EXCLUSIONS`／`OCCURRENCE_EXCLUSIONS`／`SENSE_ASSIGNMENTS`）
**每筆都必須寫理由**。詞義分裂未指定時掃描器會中止，**它不猜**。

### ④ 逐句對齊

透過舊譯的「原文」欄位把每一筆對回英文正典，**逐欄**比對。

**開工前先讀 `data/translation-issues.json`（TI-1～TI-27）。那是待辦清單，不是靠記憶。**
特別注意 `affectsOnly: "*"` 的全域通則（如 TI-4 一律第二人稱、TI-24 一律用 EoT／EoE 縮寫）。

### ⑤ 寫對齊報告 → `docs/alignment/`

格式見 §6，範例見 `docs/samples/alignment-my-life-for-yours.md`。

### ⑥ 擁有者裁決

**AI 一律標註，不自行改寫舊譯** —— 包含客觀欄位不符的情形。AI 提出建議，不直接套用。
例外：已裁決的術語由工具批次套用，標記 `term-applied` 僅供知悉。

⚠️ **裁決一經作成，同一輪內就要回寫 `data/translation-issues.json`。**
曾發生 4 項裁決只寫在報告樣張裡、從未進入該檔，
之後照待辦清單作業會整批漏掉（已補登，帶 `backfilledAt` 可稽核）。

### ⑦ 產出中文 → `data/zh-Hant/`

與 canon **同構逐段對應**。受控本地化欄位（keywords／actionType／distance／potency）
**不進這一層**，算繪時從 vocabulary 解析 —— 避免同一份資料存兩處。

⚠️ **`meta.status` 一律先寫 `draft`。**
對齊裁決完成 ≠ 資料檔已驗收；擁有者看過完整 diff 後才升 `reviewed`。
（曾有四個檔案誤標 `reviewed`，已更正。）

### ⑧ 網站

`web/`（React／Vite）。`npm run catalog` 從 `data/` 生成目錄，
`predev`／`prebuild`／`pretest` 都會自動先跑它，所以**網站不會讀到過期的資料**。

## 5. 資料佈局：哪些能手改，哪些不能

```
sources/official/…            官方 PDF（唯一內容來源，不進版控）
sources/notion-export/        舊譯（證據，凍結）
sources/glossary_old.csv      舊術語表（已匯入後凍結，不再編輯）

data/decisions.json           ★ 擁有者的裁決紀錄 —— 唯一手動編輯的術語檔
data/glossary.json            ← import-glossary.mjs 生成，不要手改
data/vocabulary/*.json        ← build-vocabulary.mjs 生成，不要手改
data/glossary-pending.json    未裁決項
data/id-ledger.json           stable id 的追加式帳本，偵測 id 被改指
data/translation-issues.json  ★ 譯文層裁決（TI-*），手動維護
data/canon/                   ★ 英文正典，人工核對後手動維護
data/zh-Hant/                 ★ 中文譯文層，手動維護
releases/m0.json              ← build-m0-release.mjs 生成
```

**裁決只改 `data/decisions.json`，再重跑腳本。不直接編輯生成物，避免雙寫。**

### 5.1 兩組容易混淆的概念

**vocabulary vs glossary** —— 受控值 vs 一般術語。
待決詞必須標明 `kind`，否則所有缺詞最後都被塞進 glossary，
glossary 就失去作為術語權威的清晰度。

**`status` vs `idStatus`** —— 兩個獨立維度：

| 欄位 | 表示 | 取值 |
|---|---|---|
| `status` | **譯名**是否批准 | `approved` / `needs-review` / `deprecated` |
| `idStatus` | **id** 能否被引用 | `stable` / `provisional` |

絕大多數條目是「id 已 stable 但譯名仍 needs-review」。
`provisional` 的 id 不得進 release manifest（CI 硬性失敗），也不得被 `entityRef` 引用。

## 6. 標記制度：三個維度，不是一套標記

同一欄位可以**同時**「結構與原文一致」且「術語尚未批准」。
混成一套標記會產生「明明 unresolved 卻算 match」的理解障礙。

**維度一 · 來源抽取**（每個**條目**一個）：`verified` / `failed`
→ 回答「我們讀出來的英文對不對」，與翻譯無關。

**維度二 · 翻譯對齊**（互斥，每欄位恰好一個）：

| 值 | 意義 |
|---|---|
| `exact` | 逐字對應，無增刪 |
| `acceptable` | 內容等價但字面不同（中文必要語序調整、允許的 flavor 改寫、`0`→`null` 正規化）。**必須逐筆寫理由** |
| `mismatch` | **客觀欄位**不符（數值、距離、門檻、動作類型、關鍵詞） |
| `missing` | 正典有、舊譯無 |
| `extra` | 舊譯有、正典無 |

> `exact` 與 `acceptable` 都不阻擋批准，差別在後者要附理由讓裁決者能否決。
> **統計摘要必須分開列出兩者筆數**，不得合併成一個「相符」數字。

**維度三 · 問題**（可多個）：`unresolved-term`／`term-conflict`／`prose-issue`／`term-applied`／`none`

`prose-issue` 的嚴重度**必須連動阻擋規則**，否則只是視覺標籤：

| 級 | 判準 | 未裁決時 |
|---|---|---|
| 🔴 high | 可能改變對象、範圍、條件、時機、數值、義務或禁止事項 | **阻擋批准** |
| 🟡 medium | 增減語意、改用縮寫或加入解釋，但暫無明確機制影響 | **阻擋批准** |
| ⚪ low | 純 flavor、語氣或修辭差異 | 不阻擋 |

### 6.1 報告的兩條硬性規則

第三批報告曾長達 500 多行、大半在證明「沒問題」，而且摘要有三處數字是錯的。
兩條規則直接對應這兩個毛病：

**(1) 任何數字都必須從清單長出來，不准用寫的。**
每個計數都要附**可以自己加一遍的來源** —— 逐條清單、逐欄表格，或一行可重跑的指令。
寫不出來源就不要寫那個數字。

**(2) 相符的欄位不逐欄展開。**
全部相符時寫一行「N 個欄位逐欄相符」。需要展開的只有三類：
**需要裁決的項目**、**新出現的結構**、**與前批不同的處理方式**。

## 7. 翻譯規則的骨架

（完整版見 `docs/translation-guide.md` §4–§7，這裡只給心智模型。）

### 7.1 先分類，再處理

| 類別 | 涵蓋 | 處理 |
|---|---|---|
| **語言無關資料** | 數值、ID、門檻、骰型、參照 | 原樣搬移，不經判斷 |
| **受控本地化** | 關鍵詞、動作類型、屬性、狀態、距離類型 | 查受控詞彙表。**決定一次、套用多次** |
| **條目專屬譯文** | 名稱、敘述、Trigger、Effect、階層文字 | 真正的翻譯判斷，**風險集中於此** |

一張典型的招式卡約 70% 屬前兩類。**審核力氣應集中在第三類。**

### 7.2 規則文字（嚴格）的四項禁令

1. **不得為求文句變化而替換同義詞。** 英文規則文字刻意扁平重複，重複是特性不是缺點。
2. **不得補上原文沒有的連接詞**（「因此」「並且」「若…則」）。
3. **不得統一原文刻意不統一的用語。** creature／target／enemy 的差別可能是機制性的。
4. **不得把模糊處寫得比原文確定 —— 也不得把確定處說成模糊。**
   前者讀起來最像「翻得好」；後者會製造假問題浪費裁決時間。

**額外必檢：限定語。** `on the target`、`adjacent`、`within N`、`willing`、`that you can see`
遺漏會擴大規則適用範圍，一律 🔴 high。

### 7.3 敘述文字 flavor（寬鬆）

專案既定做法：**允許適度改寫以求通順**，不採逐字直譯。
省略程度限定、增添不改變意象的具體化、調整句式，都不算問題。
仍不允許：改變意象本身、暗示原文沒有的機制。flavor 差異一律 ⚪ low，不阻擋批准。

### 7.4 歸一 vs 標註的界線

| 層級 | 例 | 處理 |
|---|---|---|
| **排版級 → 自動歸一** | `× 2`→`×2`、半形全形空格、階層符號改門檻徽章 | 依 §6 自動修正，不逐筆問 |
| **用詞級 → 標註待裁** | 驅邪教團／驅邪；同一概念兩種譯法 | 進報告，由擁有者裁決 |

**判準：改動是否可能抹掉刻意做的區別。** 空白與標點不會；用詞會。

### 7.5 未決項的處理 —— 停止批准，不是停止工作

「查不到就停」容易被誤解成整個條目停擺。正確規則：

1. 該欄位標 `unresolved`，**不猜、不填**
2. **繼續處理同一條目的其他欄位**
3. 該條目 `status` 不得升至 `approved`
4. 該條目不得進 release manifest

**阻擋的是批准，不是處理。**

## 8. 已知失效模式（都真的發生過）

這一節是本專案最有價值的部分。**每一條都是實際事故，不是假想。**

| 失效模式 | 發生了什麼 | 防護 |
|---|---|---|
| **流暢但錯誤** | 門檻數字錯、動作類型標錯、漏一個「不」、「或」寫成「和」——讀起來毫無異狀 | 報告強制並列英文原文；manifest 內 100% 人工核對 |
| **靜默順序錯亂** | 純文字抽取把 Heroes p.16 抽成 4→5→6→7→1→2→3，「Think 思考」被誤讀為「概念發想」 | 危險的不是亂碼（看得見），是**讀起來通順的錯亂**。用 `-layout` ＋ 圖像驗結構 ＋ 舊 CSV 交叉檢核 |
| **用錯來源產生假指控** | 拿 Rules Reference 判斷狀態文字，內容與 Heroes 不同，產出一批不存在的問題 | 抽任何條目前先確認來源分冊是 Heroes 規則正文 |
| **過早認定 schema 已完整** | 只掃 p.3／p.5 就寫「14 個招式只有三種距離形狀」，p.6 出現第四種 | 真正的風險不是抽取失敗，是**為了把新規則塞進舊結構而改變原文語意**。遇到新版式先用一個代表樣本確認，裝不下就問擁有者 |
| **照 PDF 頁面決定範圍** | 多做了三張不屬範圍的卡，事後全刪 | 範圍權威是 `docs/scope.md`，不是 PDF |
| **裁決沒回寫** | 4 項裁決只存在報告樣張裡，待辦清單看不到 | 同一輪內回寫 `translation-issues.json` |
| **憑印象寫統計** | 報告摘要三處數字錯（⚪ 寫 8 實為 11、術語寫 35 實為 56） | §6.1：數字必須從清單長出來 |
| **假裝驗證過** | 寫了 hash 卻從不比對、宣稱有測試但沒有、測試走錯路徑遮住 bug | **說「驗過了」之前先實際跑** |
| **檢查走錯路徑（誤報方向）** | `validate-terms` 的實體存在性檢查從不掃 `data/canon/`，一直警告早已建立的 9 個狀態「尚未建立」 | 檢查要驗證它真的看了該看的東西 |
| **浪費算繪成本** | 150dpi 整頁已能讀出 `up to`，仍多裁一張 300dpi | 先讀 150dpi，讀得出來就結束 |
| **過度自信的判斷理由** | 使裁決者降低警覺 | 判斷欄須標明依據原文哪一段；無法定位時標 `uncertain` |

### 8.1 「通過」不等於「正確」

這張表值得背下來：

| 東西 | 它證明什麼 | 它**不**證明什麼 |
|---|---|---|
| 抽取報告寫「✅ verified」 | 抽取當下做過逐欄核對 | **不是正式批准狀態** |
| `verify-canon-hash` 通過 | 現在的 JSON 與快照一致，**內容沒被偷改** | **完全不知道當初抽得對不對** |
| 全部測試綠燈 | 資料層結構有效 | **不證明畫面能正確呈現這些結構** |
| `canonReviewStatus` | 正式的來源驗證狀態 | —— 截至 2026-07-30 仍 **28/28 都是 `draft`** |

**不要因為 hash 通過就把狀態升成 `verified`。**

## 9. 驗證指令

改完 `data/decisions.json` 後**四個都要跑，順序不可顛倒**：

```bash
node scripts/build-vocabulary.mjs && node scripts/import-glossary.mjs && node scripts/validate-terms.mjs --commit && node scripts/build-m0-release.mjs
```

> ⚠️ 只跑其中一部分會被 `stale-decisions-hash` 擋下（實際發生過）。
> **那是機制正常運作，不是壞掉。**

驗證：

```bash
node --test "scripts/**/*.test.mjs" && node scripts/verify-canon-hash.mjs && node scripts/verify-zh-structure.mjs && node scripts/build-m0-release.mjs --check
```

唯讀報告（不動 `data/`）：

```bash
node scripts/report-m0-terms.mjs
```

**commit 前必須跑完整驗證。** 各腳本的職責：

| 腳本 | 檢查什麼 |
|---|---|
| `validate-terms` | id 重複、stable id 被改指、`approved` 缺欄位、`provisional` 進 release、同英文不同譯名被靜默丟棄 |
| `verify-canon-hash` | 正典 JSON 與 `_normalized/` 快照的內容指紋 |
| `verify-zh-structure` | 中文與正典的逐段對應（數量 ＋ 每元素非空 ＋ `Array.isArray` 三層） |
| `build-m0-release --check` | 已提交的 `releases/m0.json` 是否過期 |

⚠️ `.gitattributes` 鎖定 LF —— `normalizedHash` 是偵測正典漂移的核心機制，
換行符隨作業系統飄動會讓同一份內容算出不同雜湊。**不要移除。**

🔒 **這個 repository 必須維持 private。** `data/canon/` 含官方英文逐字原文。
「已排除 PDF」不等於「不含官方內容」。

## 10. 可移植的原則

如果你在別的專案讀到這份文件，下面七條是可以直接搬走的：

1. **先分類，再處理。** 把欄位分成「機械搬移／查表決定／真的要判斷」三類，
   審核力氣只花在第三類。這一步就砍掉七成的審核量。

2. **把「抽取對不對」與「翻譯對不對」拆成不同維度。**
   混在一個數字裡，兩邊的統計會互相污染，而且會掩蓋問題。

3. **嚴重度必須連動阻擋規則。** 不連動的分級只是視覺標籤，沒有人會照著做。

4. **未決項阻擋的是批准，不是處理。** 否則一個查不到的詞會讓整批工作停擺。

5. **任何統計數字都必須附「可以自己加一遍」的來源。**
   憑印象寫的摘要會錯，而且錯得看不出來。

6. **「檢查通過」要能說清楚它到底證明了什麼。**
   指紋相符只證明沒被改過，不證明當初對；測試綠燈只證明結構有效，不證明畫面能用。

7. **AI 標註，人裁決。** 尤其是術語 —— 一旦允許 AI 自行造詞，術語漂移會在幾輪內失控，
   而且因為每個詞單看都合理，事後很難回頭找出是哪裡開始歪的。
